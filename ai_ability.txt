AI Vocabulary Extraction Platform
也就是“基于冻结样本的离线术语生产系统”。

这套方案的核心目标不是“抽更多词”，而是：

让 AI 产出的词可追溯
让 AI 产出的词可审核
让 AI 产出的词可复现
让 AI 产出的词不污染在线检索链路
让 AI 成为候选词来源，而不是规则执行器
这和你前面定的边界是一致的，也确实接近企业搜索、知识发现、智能词库治理产品的主流设计。

一、先定总原则
第一步 AI 的最佳介入时机，不是导入时，也不是搜索时，而是：

文档完成标准化之后，术语治理之前

也就是你现有链路里：

数据接入
文档解析
清洗
分块
索引
NLP 候选词
AI Vocabulary Extract
候选词合并治理
审核发布
Topic / Rule / Search
这个时机是最合理的，因为这时具备：

有稳定文本
有向量
有 metadata
有 chunk 结构
有 doc_id
还没有进入正式规则体系
这是大厂体系里常见的“offline enrichment / offline curation”位置。

二、AI 第一阶段的职责边界
第一阶段 AI 只做一件事：

从冻结样本中提炼“可用于规则构建的语义短语”

它不做这些事：

不参与索引写入
不参与在线召回
不参与实时搜索
不直接改 query
不直接生成最终规则
不替代人工审核
所以第一阶段的角色不是 search AI，而是：

offline vocabulary miner

三、完整系统设计
建议拆成 6 个模块。

1. Content Normalization Layer
你现有 ingestion 服务继续负责：

文件解析
文本清洗
chunk 切分
embedding
Solr 落库
这一层的输出要被视为 AI 的上游标准内容层。

最关键的标准输出是：

doc_id
chunk_id
title
clean_text
chunk_content
_gl_vector
source metadata
你现在这一层已经基本具备。

2. Sample Management Layer
这一层是第一阶段 AI 的基础设施，必须单独建设。

职责：

选择样本
冻结版本
保存可追溯证据
供 AI run 使用
这层不允许动态 search 取数。

建议对象模型是：

dataset
sample_version
sample_type
sample items
其中 sample item 以 chunk 为锚点，但保存上下文。

建议 sample item 至少包含：

sample_id
dataset
sample_version
sample_type
doc_id
chunk_id
title
anchor_content
sample_content
quality_score
diversity_score
selection_reason
created_at
这里：

anchor_content 是入选 chunk
sample_content 是给 AI 的上下文片段
3. AI Extraction Run Layer
这是核心执行层。

每次抽词必须是一个独立 run，而不是散落调用。

建议 run 模型：

ai_run_id
dataset
sample_version
prompt_version
model_provider
model_name
run_status
created_at
finished_at
这层的意义是冻结 AI 生产条件，满足审计和复现要求。

4. Extraction Output Layer
AI 输出不能直接写正式词库，必须先写候选层。

建议输出结构：

term
normalized_term
doc_id
chunk_id
evidence
evidence_span
confidence
ai_run_id
sample_version
source=ai_extract
status=CANDIDATE
如果一个 term 被多个 sample 命中，要保留多条 evidence，再做 term merge。

5. Vocabulary Governance Layer
这一层你已经有雏形。

治理流程建议固定为：

CANDIDATE
REVIEWING
APPROVED
REJECTED
PUBLISHED
AI 只新增候选来源，不改变治理权属。

6. Serving Layer
AI 产出的词最终被下游消费，但必须经过治理。

被消费的位置可以是：

词库推荐
Topic 构建推荐
规则编辑提示
同义词建议
短语扩展建议
但不是直接进 runtime query rewrite。

四、最佳介入时机
你问“最佳时机”，答案是两层：

系统时机
在文档 ingestion 完成之后，周期性离线触发。

建议触发方式：

新 dataset 首次建库后
数据量达到阈值后
周期性重建 sample 后
人工点击“重建 AI 词汇候选”后
文档时机
不是每篇文档一来就抽，而是：

先进入标准内容层
再进入 sample
再触发 AI
这和大厂做法一致：AI enrichment 通常是批处理、异步、可复跑，不挂在在线主链路上。

五、第一阶段的行业标准能力要求
如果你要做到接近企业级产品水位，第一阶段至少要具备 8 个能力。

1. Freeze
AI 输入必须冻结到 sample_version。

2. Traceability
每个词必须能追到：

哪个 run
哪个 sample
哪篇文档
哪个 chunk
哪段 evidence
3. Evidence-backed extraction
每个 term 必须带 evidence，且 evidence 必须来自原文。

4. Deterministic governance
AI 输出永远先入 candidate，不直接生效。

5. Prompt versioning
prompt 是配置资产，不是写死字符串。

6. Model isolation
模型、provider、参数必须记录，便于 A/B 和替换。

7. Quality control
要有抽取后校验，不是把模型输出原样吞下去。

8. Replayability
同一 sample_version + prompt_version + model config 应可重跑对比。

这 8 条是企业级标准线。

六、sample 的标准方案
你的系统是通用平台，所以 sample 不能依赖预定义类别。最佳方案是：

chunk-centered, context-backed, quality-filtered, diversity-selected

也就是：

从 Solr 取 chunk 候选
过滤低质量 chunk
用已有 _gl_vector 做语义多样性采样
对入选 chunk 回带上下文
固定为 sample_version
这比纯随机、纯业务分类、纯聚类都更贴近你当前架构。

建议第一版 sample 规模：

候选池：2000 到 10000 chunk
最终 sample：100 到 300 条
每条 sample 输入长度：控制在适合 LLM 的窗口内
七、AI 抽词的执行方式
这里不要做“一个样本调一次模型”的粗放调用。

标准做法是：

Batch-oriented extraction run

每个 run 分批处理 sample items，例如：

每批 10 到 30 个 sample
每个 sample 单独返回结构化术语列表
批处理失败可重试
单 sample 失败不影响全 run
运行流程建议是：

创建 ai_run
锁定 dataset + sample_version + prompt_version + model config
读取 sample items
分批发给模型
结构化解析
做 evidence 校验
术语归并
写候选词表
产出 run summary
八、Prompt 设计原则
第一阶段 prompt 的目标不是“理解业务”，而是“稳健抽短语”。

prompt 必须强调：

仅从提供文本中提取
仅提取可用于构建规则的短语
不要总结主题，不要输出标签
不要生成未出现的概念
每个 term 必须附原文证据
输出结构化 JSON
允许返回空结果
建议输出单元类似：

term
evidence
reason
confidence
其中 reason 可选，给人工审核辅助，但不是必须保留到最终库。

九、后处理与质量控制
这是很多系统容易缺的地方，但实际上非常关键。

AI 输出后，必须经过后处理：

结构校验

JSON 格式正确
字段完整
term 非空
evidence 非空
证据校验

evidence 必须能在 sample_content 中定位
term 最好能在 evidence 中出现或被直接支持
规范化

去首尾空格
中英文符号归一
同形异写合并
大小写归一
噪声短语过滤
去重合并
同一个 run 内：

相同 term 合并 evidence
跨 run：
保留 run 隔离，但可建立 term aggregate view
质量评分
最终置信度建议综合：

模型置信度
evidence 强度
多样本重复出现次数
文本质量分
十、数据模型建议
你最终至少需要 4 组表。

1. dataset_samples
存冻结样本。

2. ai_vocabulary_runs
存一次抽取运行。

3. ai_vocabulary_terms
存原始 AI 术语结果。

4. candidate_vocabulary
存治理入口候选词。

其中 ai_vocabulary_terms 和 candidate_vocabulary 不建议合并。
前者是机器产物日志层，后者是业务治理层。

十一、和大厂思路一致的能力点
如果你想做到接近成熟产品思路，第一阶段要体现的是这几个能力：

离线 enrichment，而非在线耦合
基于证据的抽取，而非纯生成
版本化 sample，而非动态 search 取数
run 级治理，而非散乱调用
candidate-first，而非 direct publish
可重跑、可比较、可回溯
这就是成熟企业搜索/知识治理体系常见的设计风格。

六、Sample 生成技术方案
这里给你一版适合你当前架构的标准方案。

输入源
从 Solr chunk 索引取：

doc_id
id/chunk_id
title
chunk_content
_gl_vector
source_name
其他 metadata
候选过滤
先过滤这些：

chunk_content 为空
chunk 太短，比如 < 80 字
chunk 太长，比如 > 1500 字
特殊字符比例过高
数字比例过高
重复模板内容
明显目录/页码/页眉页脚
质量分
建议第一版算一个简单 quality_score：

长度合适加分
中文/正文字符占比高加分
句子完整加分
噪声占比高减分
Diversity Sampling
建议第一版就用 greedy diversity，不上聚类。

逻辑：

先按 quality_score 排序
依次遍历候选
如果当前 chunk 与已选样本最大相似度 < 阈值，就入选
直到 sample 数量达到目标
阈值可以先试：

0.82
0.85
0.88
上下文组装
最终喂给 AI 的 sample_content 不建议只是 anchor chunk。
建议：

前一个 chunk
当前 chunk
后一个 chunk
也可以只保留前后各 1 个，控制长度。

Vocabulary AI Phase 1 Architecture

1. 文档目标
本设计用于定义“AI 介入第一阶段”的整体架构方案。Phase 1 的目标不是让 AI 直接参与检索或规则执行，而是建设一套可复现、可追溯、可治理的离线术语生产能力。

本阶段交付的核心能力：

基于标准化内容层生成冻结样本
基于冻结样本执行 AI 术语抽取
将 AI 结果以候选术语形式进入治理流程
保证 AI 输出带 evidence、带 run、带 version
不影响现有索引、检索、运行时链路
2. 背景与问题
当前系统已具备：

数据接入
文档解析与清洗
chunk 切分
embedding 生成
Solr 索引
NLP 候选词生产
现有缺口在于：

NLP 候选词偏统计，不足以表达完整业务短语
词汇生产缺少语义抽取能力
AI 若直接接入导入链路，会破坏稳定性、可追溯性和治理边界
因此需要将 AI 设计为独立的离线术语生产层，而非在线处理器。

3. 设计目标
Phase 1 设计目标如下：

Separation
AI 与 ingestion、search、runtime 解耦

Traceability
每个术语必须追溯到 sample、run、doc、evidence

Reproducibility
同一版本 sample 可复跑，结果可比较

Governability
AI 结果仅进入候选层，不直接进入规则层

Scalability
适配通用系统，不依赖预定义业务分类

Quality
通过 sample 选择、evidence 校验、候选治理控制结果质量

4. 非目标
Phase 1 不包含以下能力：

AI 在线 query rewrite
AI 实时搜索召回
AI 自动生成并发布规则
AI 自动替代人工审核
全量主题建模与盲区检测
基于反馈的自动 prompt 学习闭环
这些能力可以属于后续 Phase 2/3。

5. 总体架构
整体架构分为 6 层：

Content Normalization Layer
Sample Management Layer
AI Extraction Layer
Validation & Aggregation Layer
Vocabulary Governance Layer
Consumption Layer
逻辑数据流如下：

原始文档进入 ingestion
文档被清洗、切块、向量化并写入 Solr
Sample Job 从 Solr chunk 中选择代表性样本，生成 sample_version
AI Run 基于 sample_version 发起术语抽取
AI 原始输出进入 validation 和 aggregation
合格结果写入 candidate vocabulary
人工审核后进入正式术语库
正式术语库供 Topic/Rule/UI 推荐消费
6. 分层设计

6.1 Content Normalization Layer
职责：

接收文件/文本/URI/网页/邮件等数据
输出统一结构化文档
完成 chunk 切分和 embedding 持久化
输入：

各类原始文档
输出：

doc_id
chunk_id
chunk_content
title
metadata
_gl_vector
说明：
该层不承担 AI 抽词职责，仅为上层提供标准内容基础。

6.2 Sample Management Layer
职责：

从标准内容层选择样本
冻结 sample 版本
保存用于 AI 的证据文本
核心原则：

sample 不是随机抽样
sample 不是 search 动态结果
sample 必须版本化
sample 必须可追溯
样本选择策略：

以 chunk 为锚点
以 chunk embedding 做多样性采样
以 quality score 做质量过滤
以 context window 组装 AI 输入文本
产出对象：

sample_version
sample_items
6.3 AI Extraction Layer
职责：

管理抽词 run
按 sample 分批调用 LLM
解析结构化术语结果
设计原则：

run 必须独立编号
run 必须绑定 sample_version
run 必须绑定 prompt_version
run 必须记录 model/provider/config
输入：

dataset
sample_version
prompt_version
model_config
输出：

ai_run
raw extracted terms
6.4 Validation & Aggregation Layer
职责：

校验模型输出结构
校验 evidence 是否来自原文
规范化 term
合并重复 term
生成可治理候选词
校验规则至少包括：

JSON 合法
term 非空
evidence 非空
evidence 能在 sample_content 中定位
term 不属于明显噪声短语
合并规则至少包括：

同 run 内相同 normalized_term 合并
聚合 evidence_count
聚合 confidence
保留代表 evidence
6.5 Vocabulary Governance Layer
职责：

承接 AI 候选词
支持人工审核
决定是否进入正式术语库
重要原则：

AI 只影响 candidate 层
不直接改变规则层
人工审核仍是生效关口
状态流建议：

CANDIDATE
APPROVED
REJECTED
PUBLISHED
6.6 Consumption Layer
职责：

为 Topic 构建提供术语推荐
为规则编辑提供短语建议
为运营和审核提供来源追踪
Phase 1 中允许的消费方式：

候选词列表展示
AI 推荐词 UI
Topic 构建时建议词
Phase 1 中不允许的消费方式：

自动修改用户查询
自动进入在线搜索逻辑
7. 核心对象
Phase 1 核心对象如下：

Dataset
业务数据集合

SampleVersion
某个数据集的一次冻结样本集合

SampleItem
一个被 AI 使用的证据片段

AIRun
一次固定条件下的 AI 抽词执行

AIRawTerm
模型原始输出术语

CandidateVocabulary
进入治理层的候选术语

这些对象之间的关系为：

一个 Dataset 有多个 SampleVersion
一个 SampleVersion 有多个 SampleItem
一个 AIRun 绑定一个 SampleVersion
一个 AIRun 产生多个 AIRawTerm
多个 AIRawTerm 聚合成 CandidateVocabulary
8. 关键标识与版本策略

8.1 Sample Version
用于冻结 AI 输入集。

要求：

新版本只新增，不覆盖
一个 sample_version 对应一组固定 sample items
sample_version 必须可回放
示例：

policy_base_v1
policy_base_v2
8.2 Prompt Version
用于冻结抽词提示词。

要求：

prompt 版本独立管理
每次 run 必须显式记录使用的 prompt_version
示例：

vocab_extract_v1
vocab_extract_v2
8.3 AI Run ID
用于标识一次抽词运行。

要求：

每次 run 唯一
与 sample_version、prompt_version、model config 绑定
示例：

run_20260401_0001
9. 数据流设计

9.1 Sample Generation Flow

从 Solr 读取 chunk 候选
过滤低质量 chunk
基于 _gl_vector 做多样性采样
回查上下文构建 sample_content
生成 sample_version
持久化 sample items
9.2 AI Extraction Flow

创建 ai_run
读取 sample items
分批调用模型
解析结构化结果
evidence 校验
写入 AI raw terms
聚合生成 candidate vocabulary
9.3 Governance Flow

审核候选词
批准或拒绝
批准词进入正式词库
被正式词库用于 Topic / Rule 推荐
10. 关键架构决策

决策 1：AI 不进入 ingestion pipeline
原因：

ingestion 追求稳定和吞吐
AI 抽词追求版本化和治理
两者职责不同
结论：
AI 作为 ingestion 之后的离线 enrichment。

决策 2：AI 基于 sample，而非实时 search
原因：

search 结果动态变化，不可复现
实时数据不可审计
prompt 输入会漂移
结论：
AI 只消费冻结的 sample_version。

决策 3：sample 以 chunk 为锚点
原因：

doc 粒度过粗
chunk 更适合表达单一语义
系统已有 chunk embedding 可复用
结论：
sample item 以 chunk 为主，但保留上下文窗口。

决策 4：AI 结果必须带 evidence
原因：

防止 hallucination
支持人工审核
支持质量回溯
结论：
无 evidence 的 term 不得进入 candidate。

决策 5：candidate-first，而非 direct publish
原因：

AI 结果不应绕过治理
业务术语属于受控资产
结论：
AI 仅新增候选来源。

11. 质量保障机制
Phase 1 质量保障由 4 层组成：

11.1 Sample 质量控制

文本长度过滤
正文密度过滤
噪声片段过滤
向量多样性控制
11.2 Prompt 控制

限定只基于原文
限定输出结构
限定术语类型
允许空结果
11.3 Output 校验

JSON schema 校验
evidence 定位校验
噪声 term 过滤
term 规范化
11.4 Human Governance

审核
批量拒绝
批量通过
evidence 查看
12. 可观测性设计
建议 Phase 1 就具备基础指标：

Sample 指标

候选池大小
最终样本数量
平均质量分
平均相似度
选样耗时
AI Run 指标

run 数量
总 sample 数
成功 sample 数
失败 sample 数
总 term 数
有效 term 数
evidence 校验失败数
平均 term/sample
治理指标

candidate 数量
审核通过率
审核拒绝率
AI 候选人工接受率
13. 安全与合规
Phase 1 要求：

sample 和 evidence 仅来自已接入的受控内容
模型调用参数可审计
敏感数据处理沿用现有清洗/脱敏规则
所有 AI 输出必须保留 run 级审计信息
14. 风险与缓解措施

风险 1：sample 偏科
缓解：

使用质量过滤 + diversity sampling
固定 sample size 范围
保留 sample generation metrics
风险 2：AI 幻觉输出
缓解：

evidence 强制要求
evidence 定位校验
无 evidence 直接丢弃
风险 3：结果不可复现
缓解：

强制 sample_version
强制 prompt_version
强制 model config 记录
风险 4：候选词过多，审核压力大
缓解：

term merge
confidence 排序
evidence_count 聚合
噪声短语过滤
15. Phase 1 交付边界
Phase 1 完成后，系统应能够：

生成 BASE sample
基于 sample 发起 AI 抽词 run
保存 raw AI terms
生成 source=ai_extract 的 candidate vocabulary
支持基于 evidence 的人工审核
Phase 1 不要求：

blind sample
topic sample
reviewer feedback 学习
AI 自动生成规则
在线 query understanding
16. 结论
Phase 1 的本质不是“把 LLM 接进来”，而是建设一条企业级的离线术语生产链路。该链路以标准内容层为输入，以冻结 sample 为边界，以 AI run 为执行单元，以 candidate vocabulary 为治理入口，从而在不破坏现有检索架构的前提下，让 AI 成为可信的词汇生产能力。
